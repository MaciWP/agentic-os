# ADR 0006 — The Mesa: projects, tickets and terminals in one window

Status: accepted (2026-10-03). Extends ADR 0003 (terminals) and ADR 0005
(projects). Amended 2026-10-05: the Mesa absorbs the projects page, takes pasted
images, its tiles move and resize, it has ready-made layouts and a focus mode, the
rail and the drawer sit left of the tiles, and the app's menu shares the top bar with
each page's own bar. Amended 2026-10-06: the node drawer is gone; its actions live on
the tree's rows and an env's command output is a tile. Amended 2026-10-13: one rail with
the Mesas over the projects, no right rail, «Copiar contexto» and a free folder (see
"One rail" below).

## Context

The projects page, the grid, the tickets and the PRs were separate pages. A
ticket or a PR reached a terminal only by launching a new one with a prompt; an
agent already running could not be handed one. Opening a project's git view or
its env commands meant leaving the terminals behind. The user works with several
terminals at once and wants to move a ticket or a PR into one of them without
leaving the page.

## Named Mesas (2026-10-07)

The single-grid persistence and navigation described below are superseded by named
Mesas. A tab strip above the central tiles creates, renames and closes Mesas. At least
one remains; each holds up to six tiles, its split layout, maximized tile and selected
project node. Tabs activate manually from the keyboard. The rail preferences stay global.

`aos.mesas` stores the versioned collection and last active id in localStorage. The
first load imports `aos.grid` and `aos.grid.layout` without deleting either legacy key.
Invalid saved data falls back to the legacy grid or an empty Mesa. Failed writes retain
in-memory changes and show a warning. This is browser-local state, not a server resource.

New links carry `mesa`; `t` and `node` are navigation intents resolved once, then replaced
by the canonical Mesa URL. An existing terminal opens its owner, bringing that terminal
into sight even if another tile was maximized. Legacy `ids/max/node` links import into
the active Mesa, omitting terminals assigned elsewhere and naming those Mesas. Unknown
Mesa ids fall back to the last available one. Browser history switches between Mesas.

A terminal belongs to at most one Mesa. Its header offers an explicit move; a full
destination is disabled. The move updates both layouts together. Git and job panels
may appear in several Mesas. Closing a Mesa releases its terminal memberships, never
stops the processes, and leaves them in the global list. A launch finishing after a
switch returns to its origin, or the active Mesa if that origin was closed. A full
Mesa can still show an unassigned terminal temporarily maximized; assigning it elsewhere
clears that temporary view.

Only the active Mesa mounts terminal views. Switching detaches the browser and reuses
the PTY host's snapshot on return; it never forces takeover from another window. The
existing global attention store supplies each tab's pending count. Selecting a tab does
not acknowledge every terminal; focus or a click on the individual tile still does.

Tabs at a glance (2026-10-07). A tab shows the most pressing phase among its terminals
(`mesaPhase`, the tile's own icons: asks, failed, turn ended, working), read from the live
list, so it survives a reload; it pulses and keeps its count while one of them is unseen.
A Mesa still called "Mesa N" names itself: its tickets ("ABC-1 +1"), else a name the user
gave one of its terminals, else an agent's session title; a shell with none keeps "Mesa N".
Its emoji rides at the start of the name ("🐛 Bugs"), so the shared workspace needs no new
field; emoji joined with a ZWJ are refused, like any format character in a name. Double
click or F2 on a tab opens one popover for both; an empty name returns to "Mesa N". A tile
header dropped on another tab moves that terminal there (`moveTerminal`); a full Mesa or a
git or job panel is refused with a notice. Dropped on the strip's free room or on "+", it
opens a new Mesa with that terminal, from any Mesa (2026-10-07). The strip never scrolls: tabs shrink to 112 px
and the rest go into a "+N" menu that keeps their state and takes drops; the active Mesa
always stays in the strip. The hover lists each terminal with its phase.
Tabs reorder by dragging one onto another (before or after by half) or with Alt+←/→. The
order is this browser's: the shared workspace keeps membership only, so `mergeWorkspace`
sorts the shared Mesas by their local index and puts new ones last. A Mesa whose last panel
leaves (moved or "Quitar") asks once whether to close it: never on load, never for the only
Mesa, never while the shared Mesas are loading, and without taking the focus from the
terminal. The check lives above the Mesa page, which remounts when the active Mesa changes.

Verification: `mesas.test.ts` covers state transitions and persistence;
`e2e/mesa-tabs.e2e.ts` covers actual shells, layouts, reload, rapid switching, keyboard,
history, attention, deferred launches and unavailable storage. Existing grid, project,
monitor and palette tests cover the shared navigation and terminal lifecycle.

## One rail (2026-10-13)

Supersedes the rail tabs, the Terminales picker and the right rail described below.

- **Mesas over projects.** The left rail stacks the Mesa list (block cards, each Mesa a
  two-line row: its name, then where its terminals run) over the projects tree, split by
  a draggable divider kept in `aos.mesa.split` (a ceiling since 2026-10-13: few Mesas take
  only what they need and leave the rest to the projects). The tab strip above the tiles is gone:
  with nine Mesas a 1280 px bar asked ~1770 px and cut every name. Rows stay Radix tabs
  (vertical), so the keyboard and screen readers keep tab semantics.
- **No Terminales tab.** The tree no longer lists terminals under its nodes, only how
  many run. A terminal in no Mesa shows under «Fuera de las Mesas» in the list, and ⌘K
  finds any terminal. An ended or lost one waits there with a ✕ that removes it (and
  «Cerrar terminadas (n)» for several): before 2026-10-13 only running ones showed, so an
  ended terminal outside every Mesa could not be closed at all.
- **No right rail.** Tickets and PRs are thin draggable rows inside the projects tree, in
  two blocks at its foot, «Tickets» and «Pull requests», after every place to work
  (2026-10-13: they sat inside the groups and pushed the repos down). Dragging onto a tile and ⌘K «Llevar a…» remain
  the ways to bring one; the row has no «Llevar a…» button. The kickoff «Empezar» stays on
  the ticket page: too heavy for a row.
- **«Copiar contexto».** `GET /api/terminals/context` answers the text an agent gets for a
  ticket or a PR (the same `ticketContext`/`prContext` as a bring without task), shown in
  a modal to copy and paste anywhere, also outside the Mesa. Read-only; classified
  `remote`.
- **Mark, then launch (2026-10-13).** A click on a row marks it (`--selected`, kept in
  `aos.projects.picked`; a link marks the node it points at), and the bar above the tree
  opens a harness, Claude on the PC's model, the checkout's git or its code there. It
  replaced a picker plus a «+» on every row: one target, fewer buttons, less text. An env
  row is a dot for its state and its commands in a line under it on hover or keyboard focus
  (Levantar/Parar by word, the rest icons, each with a tooltip). No branch on the env: only
  a checkout off the usual one (most checkouts' branch) names its own, and the ticket's
  summary is not repeated under it. A repo heading marks its main checkout and unfolds, so
  marking never needs the fold first.
  Its web hangs from the checkout of the repo a config rule names (`envs.links`, a host
  prefix per repo: the company's hosts stay out of git); hosts no rule names are not
  shown.
- **Close and drop from the list (2026-10-13).** Each Mesa row and each block carry a ✕ on
  hover: a Mesa with terminals asks first (they stay open, under «Fuera de las Mesas»), an
  empty one and a block close at once (a block's Mesas stay, without a block). The whole block
  card is a drop target: a Mesa enters it, a tile opens a new Mesa in it. A loose terminal
  drags onto any Mesa's tab or block card. The Mesa row leads with its ticket badge (from the
  objective first) and then what it is about: the user's name, else the ticket's summary.
- **Free folder.** «+ Claude» opens Claude in `terminals.scratch` (default
  `~/agentic-os-scratch`), the location `scratch` «Carpeta libre», created on its first
  launch and resolved like any other location. No permission changes: `PERMISSIONS` is
  keyed by harness and mode only.

## Decision

- **One page, two areas.** `/terminales` (nav "Mesa") holds the rail and the
  tiles (until 2026-10-06 also a node drawer). Everything that defines the view
  lives in the search string, so a reload or a link restores it: `ids` (the
  tiles, at most 6), `max` (one tile enlarged) and `node` (the node marked in the
  tree). The last tile set is also
  kept in `localStorage` for a visit without `ids`. "Quitar" on a tile only
  detaches it; the terminal keeps running. Each tile fits its own xterm and
  sends its size, and the PTY takes the size of the one view attached, so a
  terminal moved between a tile and a window resizes.
- **The rail** switches between Terminales (the picker and "Lanzar aquí"),
  Proyectos (the tree), Tickets and PR. Which list is shown is per-page state,
  not in the URL: it is a view preference, not something to share. Each rail's
  inner edge sets its width (2026-10-07), the tiles' splitter pattern: drag,
  arrows by 16 px, double click or Home back to the default. From 240 px up to
  45 % of the window, with no fixed cap so a wide screen can use it; a grip on the
  border shows it at rest; kept per rail in this browser (`rail-width:<id>`).
- **No node drawer (2026-10-06).** A 440 px drawer beside the tiles used to hold
  a node's launch row, terminals, worktree actions and env commands. It took the
  tiles' room and repeated the tree, so it went. (What follows on row buttons was
  replaced on 2026-10-13 by «Mark, then launch» above.) Each row kept in sight what it
  was used for most: an env's Levantar or Parar and its web, and one icon per
  harness plus Git, a click from launching (2026-10-07: they replaced a "+" that
  opened them as a strip of named buttons). On an env row they drop below it as one
  block when they do not fit; on any other row they stay, the name shortens, and
  what sits beside it (branch, tag, git counts) shows whole or not at all. "⋯" opens a strip under the row with the
  rest: on an env Actualizar, Logs, Ver salida and Borrar entorno…; on a repo's
  heading Nuevo worktree and, for one added from the app, Quitar repo; on a worktree the app made Quitar worktree. The strip is
  inline, not a dropdown: a menu too narrow for «Borrar entorno…» that would also race the
  remove's `<dialog>`, and the worktree form needs the room. A node's name folds
  it.
- **Git tiles (2026-10-06).** A tile id is a terminal id or `git:<encoded
  location>` (`gitTile`), so a checkout's git sits, moves, splits and counts
  against the six like a terminal, and several checkouts show at once. It has
  the terminal's header (number, chip, Ampliar, Quitar), no window of its own and
  takes no ticket or PR. ADR 0009. It opens from the row's "+".
- **Job tiles (2026-10-06).** `job:<encoded env>` (`jobTile`) shows what an
  env's newest command (Levantar, Parar, Actualizar, Borrar) writes while it runs
  and how it ended. It opens by itself when one starts, from the tree or from a
  page outside the Mesa (`useOpenTile` lands in the Mesa with it), and "Ver
  salida" opens it without running anything. Logs never ends, so it stays a real
  terminal. Costs: it counts against the six like any tile; a `git:` or `job:`
  id whose checkout or env is gone stays until removed (the job tile then says
  "ya no está" and keeps the remove's result); jobs live in the server's memory,
  so after a restart the tile says no command ran. `ponytail: no pruning of
  stale panel ids, upgrade if a stale tile is reported`. A panel tile (`isPanel`)
  is never a bring target nor a `data-terminal-id`.
- **Code tiles (2026-10-08).** `code:<encoded location>` (`codeTile`) reads a
  checkout: its folders and files, and one file in VS Code's colours. A panel tile
  like git's, opened from the row's "Código" button or from a git diff's "Abrir en
  Código". ADR 0014.
- **One place to work (2026-10-05).** The projects page is gone: `/proyectos`
  redirects into the Mesa (`node` marks the node in the tree, `t` joins the
  tiles, `tab` is dropped) and the main menu no longer
  lists it. Every link to a node or a terminal from another page (tree, agent
  monitor, palette, a launch) lands in the Mesa through one function, `mesaAt`:
  the last tile set plus that terminal, or that terminal shown alone when the
  six tiles are full, so a command asking a question is never out of sight. A
  link that brings a node opens the rail on Proyectos for that visit (the stored
  tab is left alone), with the node, the one holding it and its section
  unfolded, and the node marked (`aria-current`). It unfolds them once; the user
  can fold them again while the link stays.
- **Pasted images.** ⌘V with a PNG, JPEG, GIF or WebP in the clipboard is caught
  on the tile before xterm (which drops images), and the image wins over the
  text a screenshot tool puts beside it. It goes as base64 inside JSON on the
  same bring route (`{image: {mime, data}}`), so `local-guard` needs no
  exception; the body is capped at the route (413) and the bytes at 10 MB. The
  server checks the magic bytes against the claimed type, writes
  `data/pastes/<uuid>.<ext>` (0600, in a 0700 folder; the name is never the
  client's), drops its own files older than a week, and types the absolute path
  without Enter, escaped like a Finder drag. The bring refusals apply unchanged.
  Claude Code turns the path into `[Image #N]`; a shell just shows it.
- **Tile layout (amended 2026-10-05: splits).** The tiles lay out as a tree of
  splits, tmux style: a row puts its kids side by side, a col stacks them, and
  each split keeps its own shares, so two rows can have different column widths.
  A tile's whole header is the drag handle (its own `application/x-aos-tile`
  type, taken in the capture phase like a bring). Dropped near an edge of
  another tile (the nearest within 30 %) it takes half of that tile's place on
  that side; in the middle the two change places; on one of the four strips
  along the Mesa's sides while a tile is moved, it runs along that whole side
  with an even share. A split inside a split the same way joins it, so three
  columns are one split with two borders. Tiles are numbered, and sit in the
  page, in the tree's reading order, and every move writes `ids` in that order,
  so "Llevar a…" always matches the screen. The first layout is rows of
  columns from `gridShape`; a tile that joins splits the largest one along its
  longer side, and one that leaves collapses its split. The tree is kept in
  `localStorage` (`aos.grid.layout`), not in the URL: every page that links
  into the Mesa would have to carry it; a stored value that is not a sound tree
  (unknown keys, duplicate ids, deeper than eight) reads as nothing. Every tile
  stays a sibling under its own key wherever it is placed, so a move never
  remounts its terminal, and positions are `calc(% + px)` of the grid, so the
  browser lays them out on a resize with no measure. Below 40rem a container
  query stacks the tiles in reading order. Borders are window splitters
  (pointer and keyboard) between the kids of one split; while one is dragged
  only its line moves, and the tiles take the new size on release, so each PTY
  is resized once instead of on every frame; no tile goes below 160 × 120 px,
  counting the tiles inside a kid. From the keyboard ←/→ on the number swaps a
  tile with its neighbour; there is no keyboard split.
- **Ready-made layouts and slots (2026-10-05).** With two tiles or more the bar
  offers Columnas (one row), Cuadrícula (rows of the same width, as square as the
  count allows) and Principal (the first tile at full height, the others stacked
  beside it), in the current reading order. Cuadrícula fills its last row with
  slots: leaves whose id starts with `slot:`, kept in the same tree, never in
  `ids` and never counted toward the six (`gridIds` drops such an id from a link).
  The next terminal added takes the first slot instead of splitting the largest
  tile; a tile dropped on a slot moves there; a slot closes with its own button.
  Only Cuadrícula makes slots: "Quitar" still closes the place it leaves, since
  holes nobody asked for would only waste the room. Once the tiles change, the
  kept tree is rewritten to the one shown, so a taken slot stays taken.
- **More room for the tiles (2026-10-05).** The app's menu and each page's own bar
  share one row across the top (`PageBar` puts the page's title and controls into the
  Shell's header; below `md` they take a second line), and the menu shows icons until
  `2xl`, so a page keeps the whole width and one bar's height. From `md` the rail
  sits left of the tiles and takes its room from them, so nothing
  covers a tile and a drop always reaches one. A grid narrower than 30rem stacks its
  tiles, and a first layout uses one column only below the same width, so the tiles
  stay side by side with both open at 1280 px. A narrow tile's header gives up the
  folder, then the words of its state, then the room between its buttons, and every
  action stays. (An earlier version floated the rail and the drawer over the tiles,
  see-through during a drag. They hid the terminals the user was working in.)
  "Enfoque" hides the top bar; a small pill in the bottom right corner keeps the rail
  button, the bring status and the way out. It is page state from the Shell
  (`FocusContext`), ends when the Mesa is left and is not kept across reloads. The
  Fullscreen API was not used: its Esc would fight the terminals for the key.
- **A calmer projects tree (2026-10-05).** Envs and repos fold under a chevron,
  and so do the Entornos, group and «Otros proyectos» sections; what is open is kept on this
  browser (`aos.tree.open`); a node a link points at unfolds (see above). A folded node says how many terminals run inside it. An env's
  row is its name, its state as a coloured chip, the one command that state asks
  for and a link to its web; the branch shows only when it is not the env's name,
  and the summary of its ticket when that ticket is one of "Mis tickets" (from the
  list the Shell already reads, so no request is added). Hosts and checkouts are
  inside, the rest of its commands behind "⋯", ended env commands fold behind one line, and a terminal
  under a node no longer repeats its folder.
- **"Llevar a…" and drag.** Each ticket and PR row can be dragged onto a tile or
  sent through "Llevar a…", which lists the tiles by their number. Both call
  `POST /api/terminals/:id/bring` with `{ticket}` or `{pr: {repo, number}}`,
  never with text. The server builds the text: a shell gets the key or
  `owner/repo#N` and its link (one line, nothing runs; the key alone when Jira
  is off). An agent gets the item's **content alone**: a fixed `Context:` header
  with the link, then every field, the description and the discussion inside
  `<ticket>`/`<pr>` as data, and no instruction (a PR's diff is not included). The
  user types their own instruction after it. The text is typed **without
  Enter**: the user reads it and sends it.
- **Content or task.** A switch at the top of both rail tabs, "Al llevar: Solo
  contenido · Con tarea", kept in `localStorage` `bring-mode` and read by the ⌘K
  palette too. "Con tarea" adds `task` to the payload: `work` for personal
  tickets, `review` for teammates' tickets and PRs; the agent then gets the prompt
  a launch would (ticket or review prompt, ADR 0003). Without a task nothing tells
  the agent what to do.
- **Size.** A bring is a bracketed paste, not argv, so it takes up to 60 KB
  (`MAX_BRING_BYTES`, under the PTY host's 64 KiB `MAX_INPUT`): the description up
  to 24 KB, the newest comments in what is left, older ones counted with the link.
  A launch keeps its 16 KB argv limit.
- **Teammate reviews.** The ticket rail keeps all personal open tickets and adds
  assigned teammates' tickets in `En curso`, `Pull Request` and `In Product Review`,
  using the existing team query. These rows name the assignee and say "Para revisar".
  With "Con tarea" their bring payload is `{ticket, task: "review"}`: an agent gets
  the ticket's context with instructions to review its implementation and related
  PRs without changing files or writing to Jira/GitHub. Shells still get only the
  key and link.
  A failed team read offers a retry alongside the personal tickets.
- **Paste.** A one-line text is written as a bracketed paste when the program
  asked for it, plain otherwise. A multi-line prompt goes only as a paste
  (`paste: "only"`); a program that is not taking pastes yet refuses it
  (`no_paste`, 409), because typed bare each line would be a separate message.
- **Refusals**, the same on the page and on the server: an env command takes no
  input, a terminal that is not running takes nothing, a closed PR or a repo not
  on GitHub is rejected, and a ticket for an agent needs the Jira section. The
  page disables the tile in "Llevar a…" with the reason, and a tile refuses a
  drop it cannot take before any request.
- **Drag payload.** A drag carries only `application/x-aos-bring`, a JSON object
  with exactly one item key and, only for tickets and PRs, an optional `task`
  (`work` or `review` for a ticket, `review` for a PR), validated again on drop
  and by the server, which refuses any other key. Links inside the rows are not
  draggable. A `text/plain` copy is never set: a drop on xterm's own textarea
  would reach the PTY directly, past the server's checks. Tiles take the drop in
  the capture phase, so xterm never sees it.
- **One card per drag.** Pressing a card clears any text selection, and its
  `dragstart` clears the data before setting the item and sets the card itself
  as the drag image. Otherwise a selection left across cards (a drag started on
  a group heading) is what Chrome drags: its image shows every card in it, with
  a `text/plain` copy.
- **Jira login on a second server.** Atlassian returns the login only to the
  registered callback (`jira.callbackUrl`). A server on another port (the e2e
  one on 4318) answers `/auth/atlassian/start` with a page that names the right
  origin, instead of sending the user to an Atlassian error.

## Consequences

- Text is never run by the app. A shell user who wants the key run presses Enter
  themselves.
- An agent TUI that has not enabled bracketed paste (still starting) refuses a
  multi-line bring; the status line says so and the user retries.
- With the rail and a node open the tiles get what is left: at 1280 px two side by
  side, about 250 px each, so wide layouts want the rail closed.
- The rail is hidden below `md` while tiles are shown: one area at a time on a
  phone.
- The tile layout belongs to one browser; a link to the Mesa carries the tiles,
  not where they sit, and a browser without a kept layout starts from rows of
  columns.
- Codex and Grok were not checked with a pasted image path: both stopped on their
  own trust prompt, which is the user's decision. They get the path as text.
- Pasted images are files on disk for a week, readable by the user only.
